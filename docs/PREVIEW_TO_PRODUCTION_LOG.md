## How to maintain this file (do this, every time)

- **Preview gains a screen/feature →** add an **unticked** row (`[ ]`) in the right
  phase section, same PR/commit that changed the preview.
- **Screen/feature ported to production →** tick it (`[x]`), fill the **PR** column,
  in the same PR that ports it (see the implementation guide §9).
- **Preview design of an already-ported screen changes →** untick it (`[ ]`), add a
  note, so production is re-synced.
- Keep rows granular (tabs, sections, states) so partial progress is visible.
- Update the **Status** counts below when you tick/untick.

**Legend:** `[ ]` pending · `[x]` done in production · 🟡 = partially ported (note which parts).

## Phase 1 — Trust & correctness

- [x] **Login** (`&screen=login`) → `/login` · `LoginPage.tsx` — method → email → 6-digit code (PR #57, commit 8fd30c9). Layout/hierarchy/copy already matched the preview closely; the one real gap was a CSS bug — the global `button` reset in `index.css` sat outside any `@layer`, so (per cascade-layers rules) it unconditionally beat the SSO/email buttons' Tailwind `border`/`bg-card` utilities, leaving them borderless and non-hover-responsive app-wide on every plain `<button>` relying on utilities for border/background. Fixed by wrapping the reset in `@layer base`; swept dashboard/billing/automation/integrations/team live afterward with no regressions. Verified live: method/email-step/code-step, light+dark, 1440/390.
- [x] **Connection recovery** (`&screen=connect-error`) → `/connect` · `ConnectPage.tsx` — all recovery states (PR #57, commit acc00b3) — warning icon chip, eyebrow, heading/description per real OAuth error code (missing_params/invalid_state/session_mismatch/already_used/connection_failed/account_already_connected/account_mismatch), "What to do next" checklist, Return to Integrations (resolves the real signed-in tenant path)/Start over actions, technical-details disclosure with the real status code. Preview's extra "success" demo state intentionally not ported — the real OAuth success path never lands on this page. Verified live: all error codes, light/dark, 1440/390, keyboard tab order, and that "Return to Integrations" actually navigates to the real tenant's Integrations route.
- [x] **Invitation recovery** (`&screen=invite`) → `/invite` · `InvitationAcceptPage.tsx` — all recovery states (PR #57, commit 91a5eb1) — same icon-chip/eyebrow/heading/checklist card treatment as Connection recovery; kept the real auto-accept-on-load behavior. The preview's 4 separate demo failure states (expired/used/revoked/wrong-email) collapse into ONE real state in production — the server's `acceptTenantInvitation` query deliberately returns a single generic 400 for all four (so a stolen invitation link can't be used to probe which case applies) — ported as one honest "isn't valid" message rather than fabricating a distinction the backend doesn't expose. `missing_token` and `401 unauthenticated` are genuinely distinguishable and kept as their own states. Verified live end-to-end against the real server: missing token, a real bad-token 400, and the 401 signed-out case; light/dark/1440/390.
- [x] **Integrations** (`&screen=integrations`) → `…/integrations` · `IntegrationsPage.tsx` (PR #57, commit ee1f4d1 for the shell fix below; page itself was already ported pre-session) — production PageHeader/StatusBadge, connected-account health card (ID/last-checked/credential-expiry instead of the preview's illustrative permissions/webhook/token-status grid, since the real account model doesn't expose those — real fields only), WhatsApp/CRM "Coming soon" cards; real connect/reconnect/disconnect handlers remain authoritative. **Found and fixed a shared AccountHeader bug while running the DoD pass:** at 768–1023px the AI-tokens widget and the tenant-name/Connected-pill block didn't both fit and nothing clipped the overflow, so they visually collided on every dashboard page, not just this one — fixed by hiding the tokens widget below `lg` (still reachable via the mobile account sheet). Verified live: light/dark, 1440/1024/768/390 (no overflow, no more collision), keyboard tab order.
- [x] **Billing & usage** (`&screen=billing`) → `…/billing` · `BillingPage.tsx` / `BillingPanel.tsx` (PR #57; page itself was already ported pre-session, DoD pass this session) — reused PageHeader/Section/StatusBadge primitives; current plan and real usage allowances shown with accessible progress meters and an explicit payment-provider-not-enabled notice (the preview's "What happens at the limit?"/Plan-renewal/Payment-method/Invoices sub-panels are all "not configured" placeholders there too — production's single honest notice covers the same ground without adding not-yet-real sub-sections). Verified live: light/dark, 1440/1024/768/390 (no overflow), keyboard tab order; benefits from the shared AccountHeader fix above.
- [ ] **Knowledge base** (`&screen=knowledge`) → `…/knowledge` · `KnowledgePage.tsx` / `KnowledgeBasePanel.tsx` — 🟡 (PR #57, commit 79d20a5) added the preview's "Search source files" filter over the real, already-loaded documents. The preview's two-column source-details panel (extracted content preview, index status) and "test a question against knowledge" retrieval check are intentionally NOT ported — the real API (server/src/routes/knowledgeBase.ts) only supports list/upload/delete, no endpoint for parsed-content excerpts or retrieval testing, and inventing them would mean fabricating data/behavior. Verified live: search match/no-match, light/dark. **Non-blocking quirk found (pre-existing, not introduced by this change):** at 390px, `document.documentElement.scrollWidth` exceeds `clientWidth` by ≈257px, traced to the existing `.knowledge-table-scroll` region in `styles/precision-operations-workflows.css` (a real, widely-used production stylesheet — despite the name, it also backs `.page-billing`/`.page-integrations`/`.page-team`/`.page-analytics`/etc., it is NOT the sandboxed preview-only CSS the implementation guide's rule targets). Confirmed via a wheel/touch scroll test that the page does not actually pan — `document.body.scrollWidth` is clean (390) and real scroll gestures leave `window.scrollX` at 0, so this is a harmless `<html>`-level measurement artifact, not user-reachable. Not blocking; what still keeps this screen at 🟡 is the intentionally-unported retrieval-check/extracted-content-preview gap above.
